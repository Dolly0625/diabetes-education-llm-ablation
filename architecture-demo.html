糖尿病衛教助理：系統架構

這不是單純的聊天機器人，而是一條「輸入理解 → 臨床規劃 → 證據查詢 → 安全輸出 → 就醫整理」的資料處理流程。

先看懂這張圖

每一欄代表一個階段。白色卡片中的「做什麼」是模組責任；「輸入／輸出」說明資料在這一站如何改變。點擊任何卡片，右側會顯示口頭報告時可使用的解釋。

一個病患訊息的旅程
病患輸入 → 轉成可分析資料 → 判斷該做什麼 → 必要時查官方依據 → 產生安全回覆 → 回到 LINE

主架構：資料如何穿過系統

由左至右是一次 request 的主要順序
1｜使用者與入口
1
LINE / FastAPI
接收病患訊息，驗證 Webhook 並分流事件。
輸入：文字、音訊、圖片
輸出：標準化事件
2｜多模態感知
2
ASR / QR / OCR
把語音和照片轉成文字、藥名與信心資訊。
輸入：音訊、圖片 bytes
輸出：actual_text、藥物資料
3｜輸入安全
3
Input Guard
在任何 LLM 前先檢查 prompt injection 與心理危機。
通過：進入核心流程
阻擋：直接回安全訊息
4｜狀態與規劃
4
Memory + Planner
保存病患資料，判斷意圖、五個 TADE 槽位與資訊缺口。
輸入：文字、最近對話、病歷
輸出：structured assessment
5｜工具決策
5
Dynamic Tool Gate
依 Planner 的意圖與狀態，動態決定這一輪模型能使用哪些工具。
可能開放：RAG、產卡
可能隱藏：不符合情境的工具
6｜回答與工具
6
Talker LLM
把規劃、病歷和證據組合成病患聽得懂的回答。
分支：直接回答／查 RAG／產生備忘錄
7｜輸出安全與回覆
7
Output Guard → LINE
攔截調藥、越權確診、神效宣稱，再送回文字或卡片。
輸出：TextMessage／Flex Message／QR payload

分支 A｜需要官方依據

Talker 呼叫 search_handbook → Vector 與 Graph 檢索 → threshold 與 RRF 融合 → 把 evidence 放回 Talker → 產生白話回答。

分支 B｜資訊足夠要做就醫備忘錄

產生摘要、Flex 與 QR payload → 存入 pending_card → 病患回覆「對」後才交付，避免資料尚未核對就送出。

入口／感知安全／規劃工具決策LLM／知識輸出

1｜LINE / FastAPI：先把外部訊息接進來

LINE 傳來的事件先由 FastAPI 接收與驗證，再依事件類型分成文字、音訊或圖片。這裡的責任是「接收與分流」，不是做醫療判斷。

用一個案例理解整條流程

「我星期四要回診，最近飯前血糖約 180，最低量到 65，吃藥後會頭暈，可以先停藥嗎？」

這個案例同時觸發：藥物安全、血糖記錄、回診準備與產卡。

第一次看到時要懂的名詞

Planner
幕後規劃員，不直接對病患說話。
Talker
面向病患的 LLM，負責自然語言表達。
RAG
先查官方資料，再讓模型根據證據回答。
Tool Gate
依情境限制模型「看得到哪些工具」。
Flex Message
LINE 的結構化卡片格式。
pending_card
等待病患確認的備忘錄草稿。
